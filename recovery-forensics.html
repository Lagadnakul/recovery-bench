Re-analysis of the Phase-II experiment

The recovery ladder

The dissertation reports that three recovery strategies produced identical outcomes, and reads that as a null result about diagnosis. The raw logs say something different — and more interesting. One third of the comparison was never run, and the one real improvement in the data came from changing the patch format, not from any recovery strategy.

01

What was actually built

The thesis calls this an “agentic AI coding system.” The code is a single, stateless API call. That gap is the first thing an examiner will find.

Claimed architecture vs. implemented architecture
Also worth knowing

No temperature, top_p, or seed is set anywhere in the 30 scripts — the API default is used silently. Reproducibility is therefore zero, and Blind Retry’s entire premise (that a re-roll produces a different answer) rests on an unreported sampling setting.

The claim that needs rewriting

“Identical outcomes across the failure pool” is not supported. In Round 1, Reflection-only produced an evaluable patch for exactly one of the four genuine logic failures. A defensible sentence would be: “Across the 16 of 24 condition-task cells that produced an applicable patch, no strategy resolved any task.” That is still a real finding — and it is honest.

The other direction

On django-11283, Diagnose+Revise broke 8 previously-passing tests while Blind Retry broke none. Extra diagnostic information made that attempt actively worse — which lines up with the established finding that LLM self-correction can degrade performance. That belongs in the results chapter, not in a footnote.

04

Three strategies is the bottom of the ladder

Blind Retry, Reflection-only and Diagnose+Revise differ only in how much text gets pasted into one prompt. Everything that the reliability literature actually recommends sits above them. Select a rung to see what the agent gets, and what it costs.

05

Retrying is not free — and nobody measured it

Every strategy above L0 buys accuracy with tokens, latency and money. The dissertation reports only whether a task was resolved, so the entire cost axis is absent. Numbers below are measured from the repository.

Context per attempt
31,098
Tokens for astropy/wcs/wcs.py alone — the whole file, pasted into every single prompt, with no retrieval or search.
Growth by level
≈3×
Diagnose+Revise carries the file, the previous attempt, and trimmed test output. Same task, triple the input bill.
Hard-coded throttle
60 s
time.sleep(60) after every call. One four-task sweep across three conditions idles 12 minutes before any evaluation starts.
Evidence window
3,000
Characters kept from a 1.7 MB test log. The “execution-grounded evidence” is the last 0.2% of the output.
The metric the study needs

Recovery work is moving toward Verified Recovery Rate (recovered episodes ÷ eligible failure episodes) reported alongside recovery effort — extra tokens, extra calls, extra wall-clock. Under that pair, Nakul’s result reads: recovery rate 0% at 3× the token cost. That is a far stronger negative finding than a bare “no improvement,” because it quantifies what was wasted.

06

What to fix, in order

Ordered by how much damage each one does if an examiner finds it first.

01

Rewrite the “identical outcomes” claim

The abstract asserts something the logs contradict. Report the 16 evaluated cells and the 8 dropped ones explicitly. This is a research-integrity issue, not a presentation issue.

Integrity
02

Count the dropped patches as a result

“SEARCH block did not match” happened in a third of all cells. Give it a row in the outcome taxonomy and a number in Chapter 5 instead of letting it disappear at runtime.

Integrity
03

Report sub-test scores, not just resolved/unresolved

The 0→6 jump on django-11019 and the 8 regressions on django-11283 are already in report.json. Surfacing them converts a null result into a directional one.

Finding
04

Stop calling it an agent

Retitle to something like “single-shot LLM patch generation.” It costs nothing and removes the most obvious line of attack in the viva.

Framing
05

Set and report temperature, top_p and a seed

Currently unset in all 30 scripts. Then run each condition n≥5 times per task so “no difference” becomes a measurement rather than a single sample.

Method
06

Check whether the 4 tasks are solvable at all

Human screening of SWE-bench filtered out 68% of samples as underspecified or unfairly tested. django-11283 fails because the test calls the patched function with None — inspect all four, or move to SWE-bench Verified.

Validity
07

Fix the sample: it is 12 Django tasks in a row

The 20 “pilot” tasks are the first 20 alphabetically — astropy and django only, from 2 of 11 repositories. Draw a stratified random sample instead and say so.

Validity
08

Add one rung above L2

A single additional condition — constrained decoding, or letting the model run the tests itself — turns a flat null into a trend, and answers “why only the obvious three?” before it is asked.

Upgrade
09

Report cost alongside outcome

Tokens, calls and wall-clock per recovery attempt. Free to extract, and it is the axis every practitioner cares about.

Upgrade
10

Disclose the RECITATION exclusion

astropy-14182 was dropped because the model’s safety filter blocked it as memorised training data. That is a contamination signal worth a paragraph, not a silent exclusion.
