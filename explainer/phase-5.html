What the three conditions actually are

Reading your Python scripts side by side makes something clear that the chapter states but the code makes vivid: each condition adds exactly one thing to the one before it. Nothing else changes.

The prompts were not retyped

The prompt is the experiment. If this rebuild worded things even slightly differently, new results would not be comparable with your Chapter 5 — and no ordinary test would notice, because everything would still work on a subtly different prompt.

So the templates are extracted mechanically from your Python scripts into a committed file, along with the fingerprint of each source file. Two checks run:

CheckWhat it proves
The rebuilt prompt equals the stored template with values filled inNo drift in the reimplementation
The stored template appears verbatim inside your original scriptThe stored copy is genuinely yours, not a paraphrase

Your own words, checked by a machine.

This is the same trick as phase 3's byte-identical table, applied to the input rather than the output. Between the two, both ends of your experiment are now pinned: the prompts that went in and the numbers that came out.

Being told which file to fix

Your scripts pick the file to edit out of the reference solution — the known correct patch. The model is told where to look. Your dissertation states this plainly and uses the technical name for it: oracle localisation, in a system described as “single-shot, oracle-localised, single-file patch generation.”

Since it is declared method, phase 5 reproduces it exactly rather than improving it. But two things were worth checking.

Does the answer leak? The model is told the file path. It must never see the reference patch itself, or it would be handed the fix. A test now takes a task whose correct answer is recognisable, builds the real prompt, and asserts the current file is present while the solution is absent.

The boundary this project cannot cross

Here is the honest difficulty, and it is worth understanding properly because someone may ask you about it.

Diagnose+Revise is defined by giving the model the real result of running its patch against the real test suite. The prompt says so to the model in as many words: “the REAL, ACTUAL result of running your previous patch against the real test suite (ground truth, not a guess)”.

This pipeline cannot run tests. It deliberately uses no Docker — that is the decision that makes everything reproducible on a laptop in seconds. But it means that for any new task, the strongest evidence available is git refusing the patch. Real, but not the same thing.

Two consequences follow, both deliberate. An apply failure found in your archive is labelled an apply error, not test output — being in the archive does not change what it is. And a cell with no evidence is refused outright and the refusal recorded, rather than run as Reflection-only under a Diagnose+Revise label.

What that does not say.

It does not say the bug is fixed. Nobody ran the tests, because nothing here can. The row says verification: apply and its resolved field is empty by type — the safeguard from phase 1, doing its job on the very first live result. A patch that applies is a real, checkable fact; “this resolves the issue” is a different claim and this pipeline is not entitled to make it.

Every path ends in a record

One function runs every condition, so any difference in results comes from the prompt and nothing else. Your original had a separate script per condition, each edited between runs — which means a difference in handling could never be ruled out as the cause of a difference in outcome.

That function has one absolute rule: it always returns a result. There is no path — refusal, budget stop, provider failure, unreadable response, rejected patch — on which a cell can quietly disappear. This is the defect the whole project exists to prevent, and the one phase 3 found 22 real instances of in your original data. Ten tests, one per path, hold it in place.

What was left undone, and why

Your configuration asks for a cleverer context setting: send only the relevant function instead of the whole file, which would cut a 3,300-line file from 31,000 tokens to about 3,000 and is what makes repeat runs affordable.

It is not implemented yet, for a reason worth stating. To send only the relevant function, something has to decide which function — and the reliable source for that is the reference solution's line numbers. That would be giving the system more of the answer than the file path alone. Oracle localisation is already declared method; oracle symbol selection is a further step that changes what the system is, and it deserves a deliberate decision and an explicit disclosure rather than arriving as a quiet default.

Also permanent: your Round 2 cannot be replayed cell-for-cell. It fed the model the full round-1 response, and those raw text files were deleted long ago. The patches survive; the prose does not. New multi-round runs are unaffected, because this pipeline keeps each round's full response.

Where this leaves the project

Six of nine phases done. The pipeline can now take a real task, build your exact prompt, call a real model under an enforced budget, turn the reply into a patch, and get a real verdict from git — recording every step, including the parts it is not entitled to claim.

Next was phase 6: the sweep. Phase 5 proved one cell works; phase 6 is the claim that when hundreds run, none of them can go missing. Two numbers from the live cell size it — 2,251 tokens and 135 seconds each, so a 120-cell arm is about four and a half hours and well inside the budget ceiling.
