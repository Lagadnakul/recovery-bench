Know when to stop

When an AI coding agent fails, it retries. It retries whether retrying can work or not. We are building the part that is missing: a rule that decides, after each failure, whether another attempt is worth making — or whether the agent should stop and ask a human one question.

Lagad Nakul Kiran · 2503032340022 PIET, Parul University working title — not final

01

The problem, without jargon

Give a junior developer a bug. He writes a fix. The test fails. A senior engineer standing behind him asks one question before anything else: was he careless, or does he not understand?

careless

He understood the bug perfectly. He put the fix in the wrong place, or broke the formatting, or miscounted a line. The right response is “try again” — he will get it in thirty seconds.

confused

He does not know what is wrong. His fix was clean, neat, well written, and solving the wrong problem. “Try again” is useless. He will produce the same wrong idea in tidier handwriting.

A human makes that call instantly. No AI coding agent makes it at all. Cursor, Claude Code, Copilot, mini-SWE-agent — every one of them responds to a failed test the same way, every time: try again. Nothing in any of them asks whether trying again can possibly work.

Three things go wrong, not one

Money

A coding agent burns 50,000–200,000 tokens per resolved issue, roughly $1.50–$6. On the issues it cannot resolve, it burns the same and gets nothing.

It gets dumber

Every failed attempt is appended to the conversation. Measured accuracy falls as context grows even when nothing relevant was removed — 13.9% to 85%. The agent retries its way into being less capable.

Nobody was told

The one person who could have unblocked it in twenty seconds was never asked. The agent failed quietly, expensively, alone.

02

What I found in the current research

This is not a hunch. Between April and September 2026 several groups published the same observation from different directions, and one of them built a benchmark for it.

Agents genuinely cannot tell when they are stuck

HiL-Bench (April 2026) tests exactly this. Give a frontier model a task with a piece of information deliberately missing, and give it a button labelled “ask a human”. Then see what happens.

ConditionSuccessWhat it shows
Complete information given 75–89% Capability is not the bottleneck
Information missing — must decide whether to ask 4–24% Judgement is the bottleneck

Their failure analysis, per model family, is worth quoting in the thesis:

  • GPT family — does not notice the gap at all. Executes confidently on a wrong belief. Giving it the ask-a-human button barely changes its behaviour, because it never thinks to press it.
  • Claude — says out loud that it is stuck, and then submits anyway. This accounts for 45% of its failures. Detection without action.
  • Gemini — asks constantly on easy problems and stops asking on hard ones. Exactly backwards.

Retrying does not fix reasoning. This is settled.

The original result (ICLR 2024) and its 2026 follow-ups agree: a model cannot reliably correct its own reasoning without an outside signal. GPT-4 on GSM8K goes 95.5% → 91.5% → 89.0% across two rounds of self-correction. It gets worse, not better. A 2026 paper adds the Accuracy Correction Paradox: weaker models self-correct more often, because they are guessing either way.

The field has asked for exactly this kind of work

Two 2026 position papers argue the SWE-bench leaderboard can no longer tell its top entries apart, and that what should be measured instead is failure-mode profiles and cost-efficiency. A third argues coding benchmarks miss collaboration entirely. That is the gap this project sits in, and we can cite it rather than claim it.

⚠

Be honest about the crowd. HiL-Bench, SWE-Touch, SWE-Together and Dialogue SWE-Bench all appeared in 2026. “Agents should ask for help” is not a new claim. Our contribution has to be narrower than that — and it is.

03

The gap nobody has filled

Every existing paper treats “should I ask for help?” as one question with one answer. It is not one question. It has two answers, and they are opposites.

A careless failure is the worst thing to escalate. The agent can fix it alone, instantly, for almost nothing. Interrupting a human is pure waste.

A confused failure is the worst thing to retry. It will never succeed, and every attempt burns money and context on the way to the same wrong answer.

So the decision to escalate must be conditioned on what kind of failure it was. No published policy does this. That is the thesis.

The useful part is that the failure class is not something we have to predict. It is something we can observe, exactly, for free:

ObservationClassCorrect response
Patch would not apply — git apply rejected itCARELESSRetry
Patch applied cleanly, test still failsCONFUSEDEscalate
Container died, network error, quota exhaustedBROKENAbort — measured nothing
No new progress across several stepsLOSTEscalate

This is a strength, not a shortcut. The signal is trivially cheap and perfectly reliable — and nobody is using it to make a decision that costs real money.

04

The algorithm

This is the question the professor asked, and it is the right question. A set of if-statements is a heuristic, not an algorithm. Here is the actual formulation.

Deciding whether to make one more attempt or to stop is a known class of problem: optimal stopping under uncertainty — the same family as Wald’s sequential probability ratio test. We are instantiating it for agentic program repair, with one modification that is ours.

Class-Conditioned Optimal Stopping — CC-OS

Maintain a belief about whether one more attempt will succeed. Condition that belief on the observed failure class. Stop when the expected value of asking exceeds the expected value of trying again.

Step 1 — Observe the class

A deterministic function of the trajectory, not a classifier. It reads exit codes, not intentions, so it cannot be wrong and introduces no confound. 

# deterministic; O(1); no model call
def triage(attempt) -> Class:
    if attempt.apply_failed:        return CARELESS
    if attempt.infra_error:         return BROKEN
    if attempt.no_progress(window=3): return LOST
    return CONFUSED   # applied cleanly, test still red

Step 2 — Hold a belief, and let it decay

Step 4 — Why this answers the professor

Because the policy is derived, not written. Nobody hard-codes “retry formatting errors.” The algorithm learns that p(CARELESS) is high and p(CONFUSED) is near zero from the data, and the inequality then produces the correct behaviour on its own. If a future model changes those probabilities, the policy changes with it, with no code edit.

And all four experiment arms are one algorithm

This is the part that makes the comparison clean: the baselines are not separate programs. They are the same rule at different values of θ.

ArmSettingBehaviourRepresents
A · Stubborn θ = −∞ Never escalates Every agent shipping today
B · Needy θ = +∞ Escalates on first failure The naive “add a human” answer
C · Random p ~ Bern(ρ) Ignores class; escalation rate ρ matched to D The control that makes it science
D · CC-OS θ = θc Class-conditioned stopping rule Our contribution

Arm C is what protects Nakul in the viva. Without it an examiner says “of course D won, you gave it human help.” With it, C received exactly the same number of interruptions, placed without regard to failure class. If D beats C, the finding is:

It is not how much you help. It is whether you help at the right moment.

A second, smaller algorithm: the circuit breaker

LOST needs its own detector, since there is no exit code for “going in circles.” Define a progress score per step as the novelty of the action against everything tried so far — Jaccard distance over the set of files touched and command n-grams — and break when its moving average over a window falls below ε. Published work on agent circuit breakers reports loop traps exiting at 10 steps instead of 30.

Cost of the whole thing

Triage O(1). Belief update O(1). Stopping rule O(K), precomputed once. Progress score O(m) over a short window. Against a single LLM call, all of it is free. That is worth stating explicitly — the contribution costs nothing to run, which is precisely why not having it is indefensible.

05

What gets measured

Not accuracy alone. The 2026 literature is explicit that accuracy no longer separates agents, and that cost does.

Solved

Bugs actually fixed, by the real test suite. The obvious one, and not the interesting one.

● headline

Human taps

How many times the bell rang. Humans are the scarce resource in this system, not tokens.

● new

Wasted tokens

Tokens spent on attempts that could never have succeeded. As far as I can find, nobody has published this number.

Context at stop

How bloated the conversation got before it gave up. Connects the result directly to the context-rot literature.

Steps to decision

How fast the referee knew. A rule that takes forty turns to call it is worthless even if it calls it correctly.

Ask-F1

Precision of questions against recall of blockers. Included so our numbers are directly comparable with HiL-Bench.

The one picture

The simulated human

Nobody can sit and answer questions for four hundred runs. Every benchmark bug ships with its official correct fix, so when the agent rings the bell an oracle answers one question, once, from that fix. That measures how much a perfect senior engineer would have helped — an upper bound, declared as one. Then twenty bugs are run with a real human for calibration, which doubles as the viva demo.

How it gets built

Two programs that never talk to each other directly. The engine appends events to a file; the dashboard reads the file.

engine — the instrument

mini-SWE-agent as the agent: about 100 lines, bash only, linear history. It replaced SWE-agent in 2026 and scores above 74% on SWE-bench Verified.

Our referee wraps it. Its control flow already runs on exceptions — Submitted, LimitsExceeded, FormatError — so adding Escalated is a natural extension rather than a fight.

Next 16, React 19, Tailwind v4, shadcn, framer-motion, recharts. The same stack as the Kuotivo dashboard, so none of it is new ground.

It tails the engine’s event file over SSE, which means it works on a finished run and on a live one with no change.

class Escalated(InterruptAgentFlow):
    """The agent stopped and asked. This class is the thesis."""

class RefereeAgent(DefaultAgent):
    def step(self):
        try:
            return super().step()
        except TestFailed as f:
            c = triage(f)
            emit({"event": "triage", "class": c, **meter()})
            if p(c, self.k) <= theta[c]:
                raise Escalated(question_for(c, f))

The disk problem is solved

SWE-bench normally wants about 120 GB of Docker disk. We do not have to pay that.

RouteDiskNotes
Build images locally, default settings ~120 GB The documented requirement. Not happening on this machine.
Epoch AI prebuilt registry ~30 GB All 500 Verified instances, MIT licensed, pull instead of build — a 6× reduction. For the ~100 we need, roughly 6–8 GB.
Prune between instances steady --clean=True plus docker image prune. Holds disk flat regardless of how many bugs we run.
Modal / sb-cli cloud evaluation 0 GB Runs the harness entirely off-machine. Fallback if local still fights us.

So the answer is: pull, do not build; run a subset, not all 500; prune as you go. Realistic steady state is well under 15 GB. One caution worth recording — the images are x86, so on Apple Silicon they run under emulation. Slower, not blocking.

Still open

  • The name. “Know When to Stop” is a placeholder. The title is the first thing the examiner reads, so it is worth deciding deliberately.
  • How generous the oracle is. One question per escalation is the current cap. It needs to be defended, or it becomes the attack.
  • What if D does not beat C. That is still a publishable result: placement does not matter, only volume does. Worth deciding now how it would be written, so the finding is not steered toward the hoped-for answer.
  • Second model. One model carries the main experiment; a second is a robustness check if time allows.
